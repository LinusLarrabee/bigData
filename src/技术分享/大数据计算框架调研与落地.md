# 一、用例引入-WordCount

## 1.1 MapReduce介绍

**传统算法：单机性能限制**

**分布式算法：多机性能扩展**

1. input : 读取文本文件；
2. splitting : 将文件按照行进行拆分，此时得到的 K1 行数， V1 表示对应行的文本内容；
3. mapping : 并行将每一行按照空格进行拆分，拆分得到的 List(K2,V2) ，其中 K2 代表每一个单词，由于是做词频统计，所以 V2 的值为 1，代表出现 1 次；
4. shuffling：由于 Mapping 操作可能是在不同的机器上并行处理的，所以需要通过 shuffling 将相同 key 值的数据分发到同一个节点上去合并，这样才能统计出最终的结果，此时得到 K2 为每一个单词， List(V2) 为可迭代集合， V2 就是 Mapping 中的 V2；
5. Reducing : 这里的案例是统计单词出现的总次数，所以 Reducing 对 List(V2) 进行归约求和操作，最终输出。

![image-20240720104259692](img/posts/大数据计算框架调研与落地.asserts/image-20240720104259692.png)

## 1.2 底层实现：分布式物理机架构

在分布式系统下：

- splitting 将 input 拆解的多行分配给多个物理机做后续的 Mapping 操作
- Shuffling 将 Mapping 的结果重新组合交给多个物理机做 Reducing
- Result 会将 Reducing 的多个结果进行展示
- Map：在单个节点上，可以对输入数据进行分割并执行映射操作，生成中间键值对。
- Reducce：单个节点上的 Reducer 处理分组后的数据，合并相同键的所有值。

**效果：增加split shuffle 和 final result 的成本，但是提高 map 和 Reduce 环节的效率。**

## Hadoop

### 介绍

Hadoop 是一个用于存储和处理大规模数据的开源框架。它由多个模块组成，主要包括：

- Hadoop Common：提供 Hadoop 生态系统的通用实用工具。
- HDFS (Hadoop Distributed File System)：一个分布式文件系统，提供高吞吐量的数据访问。
- YARN (Yet Another Resource Negotiator)：用于作业调度和集群资源管理。
- MapReduce：一种基于 YARN 的编程模型，用于大规模数据处理。

实现了一种基本思路：**数据存储框架+计算引擎**。

### MapReduce限制

迭代性能：

MapReduce 框架不是为迭代计算设计的。每次迭代都需要从头开始读取数据，处理完毕后再将结果写入磁盘，这导致了大量的磁盘 I/O 操作，使得迭代计算非常低效。

（相比之下Flink和Spark使用内存计算，在需要进行迭代计算时更高效）

状态管理：

在 MapReduce 中，维护算法状态（比如配置项job的设置）需要手动实现，通常通过多次读写磁盘来保持迭代间的状态。这增加了复杂性并降低了性能。

（相比之下Flink有很强的状态管理功能，Spark需要在跨批次处理时维护）

### Spark简介

宏观构建：

- Spark sql 结构化处理数据。
- Spark Streaming 的本质是微批处理，它将数据流进行极小粒度的拆分，拆分为多个批处理，从而达到接近于流处理的效果。
- Mllib & GraphX：自有机器学习和图像绘制生态。

![image-20240720105518585](img/posts/大数据计算框架调研与落地.asserts/image-20240720105518585.png)



数据结构抽象：

- RDD：函数式编程（上述WordCount）定义了大量算子操作，非结构化数据（流媒体，字符流）
- Structured APIs：结构化数据(RDBMS)和半结构化（日志）性能更好，RDD算子抽象形成SparkQL工具集。

![image-20240720105524272](img/posts/大数据计算框架调研与落地.asserts/image-20240720105524272.png)





### Flink简介

1. 实现逻辑：基于事件逐条驱动，批处理视作有界的流。
2. Low API：Spark提供的Low API为RDD，提供了数据更多的操作空间，Flink提供的Low API提供的是更精细化的时间和状态管理。

### 计算框架使用

针对不同的数据形式和需求，需要使用不同的框架。

![image-20240720105602937](img/posts/大数据计算框架调研与落地.asserts/image-20240720105602937.png)

|               | **Spark**                                                    | **Flink**                                                    |
| ------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **公司业务**  | 业务上无明显实时性要求。                                     | （建议在不同场景下选择不同的计算框架）                       |
| 易用性        | 提供简洁的API，支持Scala、Java、Python和R                    | 支持Java和Scala，Python支持不成熟，如需绘制图像还需分步导出数据再Python写脚本绘制 |
| 生态系统丰富: | 集成了SQL、机器学习（MLlib）、图计算（GraphX）等多种工具。   | 相比Spark，Flink的社区，文档和生态系统较小                   |
| 高性能        | 延迟计算优化：内存计算，提高了数据处理速度，因此资源损耗大。 | 事件驱动，逐条处理。针对流处理和批处理进行了深度优化         |
| 实时性        | Spark  Streaming的微批处理模型在处理实时数据时存在一定延迟。一般在1-2秒，优化后可达到100-500毫秒。 | 真正的流处理，高频数据流处理通常在10-100毫秒。               |
| 状态管理      | 有限的状态管理功能，依赖外部存储系统和检查点机制，回复时间较长。 | 内置状态管理功能。                                           |
| 应用场景      | 大规模数据处理、机器学习、批处理、图计算                     | 实时数据处理、低延迟应用                                     |
