# 一，迁移原则 

平滑迁移，迁移过程中调用链不能中断，不影响业务。

# 二、幂等性保证

qoe迁移的部分包含对qoe数据的计算和存储，涉及大量对中间件的写入，aka，qoe业务下游。考虑到迁移系统在极端情况下可能对qoe业务下游产生双写现象，下表描述的对业务下游的潜在影响。

幂等性与回滚操作关注点：

|                     | 特点                                                         | 涉及范围                                                     | 额外解决                                                     |
| ------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| kafka写入           | 双写会导致数据重复，但新版eventcenter本身也会导致数据重复    | WIFI_QUALITY_COUNT_EVENT:Statistic, KAFKA_TOPIC_TAUCEVENT_NETWORK_HEALTH_QOE:GeoMap | 此处的幂等性需要下游自行保证，GeoMap只维护最新数据且做了幂等校验，statistic |
| cassandra写入       | 主键为trId保证唯一性，支持回滚时重新写入数据                 | AP，Client数据存储                                           |                                                              |
| network写入         | network表为最新状态，因此无数据重新写入必要                  | IspNetworkClientPO                                           | network修改此处逻辑                                          |
| S3写入              | 写S3的代码本身没有重复校验，不支持幂等与回滚，只能硬切。     | 原有wifi-management overdue业务逻辑                          | 可在下游新增重复校验                                         |
| redis写入           | redis自行保证                                                | 中间计算所需数据                                             |                                                              |
| mongo写入           |                                                              | activity读写alert                                            |                                                              |
| network/account读取 | 涉及到读取network/account表的信息，可能两次读取结果不一致导致校验异常 |                                                              | 可考虑设置redis缓存读取的network表内容                       |

架构

1. 在redis构建去重表，防止双写事件发生
2. 在数据源进行幂等性操作，减轻双写影响。

操作：

1. 使用aop及apollo进行迁移控制，在切换时使用硬切换。
2. 数据回写操作只保证原有cassandra的表及其他存储历史信息的表回归正常。
