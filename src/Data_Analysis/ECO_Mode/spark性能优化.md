# 当前性能瓶颈

## 数据源

当前系统配置的数据源使用txt.gz2格式，每个文件存放1000条qoe原始数据，体积约200-300KB，而spark处理数据一般在128MB，存储格式为parquet较为合适。



此处的解决方案是

1. 修改数据上报的消息体数目
2. 在微服务中直接将数据处理成128MB，parquet格式（不建议在流侧操作过多）

## 数据处理

目前在使用spark操作s3存放的qoe原始文件

```python
df = spark.createDataFrame([], StringType()).toDF("value")  # 初始化空的 DataFrame

for date_str in generate_date_range(start_date, end_date):
    input_path = f's3://{bucket}/{input_prefix}/{date_str}/messages-*.txt.gz'
    try:

        # # 使用Spark列出符合条件的文件（以messages-开头，.txt.gz结尾）
        # df = spark.read.text(input_path)
        #
        # # 显示 DataFrame 内容（可选）
        # df.show(truncate=False)


        file_rdd = sc.textFile(input_path)
        json_list = file_rdd.zipWithIndex().filter(lambda x: (x[1] + 1) % 2 == 0).map(lambda x: json.loads(x[0])).collect()
        df_day = spark.createDataFrame(json_list, StringType()).toDF("value")
        df = df.union(df_day)

    except Exception as e:
        print(f"Path not found or error processing: {input_path}, skipping. Error: {e}")

```



这个写法在测试环境使用10.26-10.27两天的数据进行计算时，进行df.union(df_day)会因读取过多文件导致EMR无法继续执行。

解决方案有两步，按每天的原始数据去处理，按每条消息进行处理。



Spark提供对单一路径的扫描方式，

直接使用 input_path = f's3://{bucket}/{input_prefix}/{date_str}/messages-*.txt.gz' 的方式加载数据，是可以通过 Spark 的 sc.textFile 或 spark.read 加载 S3 上的多个文件的，但问题在于 **所有匹配的文件会被 Spark 作为一个整体的 RDD 或 DataFrame 处理**，无法实现单个文件独立处理的逻辑。



如需要提前获取文件列表，则需要在每个emr执行节点使用 boto3 或 Hadoop FileSystem 提前获取文件列表。

目前的解决方案是先尝试按天将数据进行处理，如仍无法处理，则使用boto3来提取文件列表进行操作。
